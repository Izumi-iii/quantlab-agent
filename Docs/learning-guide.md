# QuantLab Agent 学习指南

> 当前进度：M1 确定性分析核心  
> 最近更新：2026-10-01  
> 使用方法：先读“心智模型”，再按代码阅读顺序打开文件，最后独立回答自测问题。每完成一个里程碑继续补充本文。

## 1. 先建立整体心智模型

这个项目最终要完成一条链路：

```text
用户问题
  → Agent 理解意图并选择工具
  → 工具校验参数
  → 确定性程序检查数据和计算
  → 图表与报告引用计算证据
  → 用户看到结果、限制和执行过程
```

M1 只实现其中最底部、也最重要的一段：

```text
CSV 字节
  → DatasetService
  → 不可变 Dataset 快照
  → AnalysisService
  → 固定区间的 Analysis 快照
  → 指标函数
  → MetricResult
```

暂时没有 Agent、网页和模型 API。这不是项目缺失，而是实施顺序：如果底层计算不可信，Agent 只会更快地传播错误。

## 2. 为什么先做确定性核心

语言模型擅长理解“比较这两个资产去年下半年的表现”这样的自然语言，但它不应该负责关键数字。原因包括：

- 模型生成文本具有概率性，相同请求不保证逐字一致。
- 模型可能遗漏重复日期、非法价格和价格口径冲突。
- 数值计算需要可以用手工样例和单元测试验证。
- 工具失败时，模型可能仍组织出一段语气自然但没有依据的回答。

我们的分工是：模型提出“要做什么”，程序验证“能不能做”并完成“怎么算”。

## 4. Python 项目基础

### 4.1 `pyproject.toml`

它是项目的构建和依赖入口：

- `requires-python` 声明支持的 Python 版本。
- `dependencies` 是运行代码需要的库。
- `project.optional-dependencies.dev` 是测试等开发依赖。
- `tool.setuptools.packages.find` 告诉构建工具源码在 `src` 下。
- `tool.pytest.ini_options` 告诉 pytest 从 `tests` 收集测试。

`pip install -e ".[dev]"` 中：

- `-e` 表示 editable install。修改 `src` 后不需要重复安装项目。
- `.` 表示安装当前项目。
- `[dev]` 表示同时安装开发依赖。

### 4.2 为什么使用 `src` 布局

如果包直接放在仓库根目录，测试可能因为当前目录恰好可见而成功，但安装后的包实际有问题。`src` 布局迫使测试通过正常安装路径导入 `quantlab_agent`，更接近用户运行方式。

### 4.3 虚拟环境

`.venv` 为这个项目保存独立依赖，避免污染系统 Python。它已被 `.gitignore` 忽略，不提交到仓库。

常用命令：

```powershell
# 安装项目与测试依赖
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"

# 运行全部测试
.\.venv\Scripts\python.exe -m pytest

# 只运行一个测试文件
.\.venv\Scripts\python.exe -m pytest tests\unit\test_metrics.py

# 显示某个失败测试的更多上下文
.\.venv\Scripts\python.exe -m pytest -vv tests\unit\test_datasets.py
```

本次实际验证环境：Python 3.14.0、NumPy 2.5.3、pandas 3.0.6、Pydantic 2.13.5、pytest 9.1.1。`pyproject.toml` 使用兼容范围，尚未建立精确锁文件。

## 5. 数据契约：Pydantic 模型

`domain/models.py` 定义系统边界上的结构化对象。Pydantic 的作用是：创建对象时检查类型、必填字段和业务约束，并能稳定地序列化为 JSON。

例如 `DatasetMetadata` 保存：

- 资产标识；
- 数据来源声明；
- 价格口径；
- 币种与频率；
- 用户是否声明日线完整；
- 数据是否为合成样例。

`extra="forbid"` 表示出现未定义字段时直接报错，防止拼错字段名后被静默忽略。`frozen=True` 阻止字段被重新赋值。

需要注意：冻结模型并不能自动冻结任意嵌套对象。因此我们没有把可修改的 DataFrame 保存在 Dataset 快照里，而是保存 `tuple[PricePoint, ...]`。每次计算需要 pandas Series 时重新创建一份临时对象。

### 为什么使用枚举

`PriceBasis`、`MetricName`、`ErrorCode` 使用枚举，避免在各处散落容易拼错的字符串。例如代码判断的是 `MetricName.MAX_DRAWDOWN`，而不是随意比较 `"max_drawdown"`。

## 6. CSV 导入与质量门禁

`DatasetService.import_csv` 接收原始字节，而不是直接接收文件路径。这有两个好处：

1. 将来 Streamlit 上传组件本来就提供字节。
2. 领域服务不需要访问用户指定的任意本地路径。

检查顺序大致为：

1. 文件是否为空、是否超过大小限制。
2. 是否为 UTF-8／UTF-8 BOM。
3. CSV 是否可解析、行数是否超限。
4. 是否包含 `date` 和 `close`。
5. 日期是否严格采用 `YYYY-MM-DD`。
6. 收盘价是否为有限正数。
7. 日期是否重复。
8. 是否为首版支持的日线数据。
9. 是否需要排序、是否有异常大涨跌。
10. 生成规范化内容哈希和数据快照。

### 错误与警告不同

- 错误会阻止创建 Dataset，例如缺列、重复日期、价格为 0。
- 警告允许创建 Dataset，但后续可能限制能力，例如价格口径未知、日线完整性未确认。

日期未排序属于可以确定修复的问题：程序使用稳定排序，并把转换写入质量报告。重复日期不自动去重，因为系统不知道应该保留哪一条。

### 为什么记录两个 SHA-256

- `raw_sha256` 对原始上传字节计算，回答“用户上传的是哪一个文件”。
- `normalized_sha256` 对排序和格式统一后的内容计算，回答“分析使用的是哪一份规范化数据”。

两者可能相同，也可能不同。原文件本来就是规范格式时，相同完全正常。

## 7. 分析准备与日期对齐

`AnalysisService.prepare` 不直接计算指标，它先建立 `AnalysisSpec`，明确：

- 使用哪些 dataset_id；
- 请求区间与实际区间；
- 请求哪些指标；
- 两资产如何对齐；
- 每个资产排除了多少观测；
- 哪些指标当前可以计算；
- 年化因子是多少。

这种“先固定分析条件、再计算”的方式避免报告、图表和指标分别选择了不同数据。

### 两资产为什么取共同日期

假设 A 有 1、2、3、4 日价格，B 只有 1、3、4 日价格。直接把两列按行号排列，会把 A 的 2 日价格和 B 的 3 日价格错误配对。系统按日期索引取交集，得到 1、3、4 日。

但这时 1 日到 3 日是跨两天收益，不能假装成单日收益再乘 `sqrt(252)` 年化。因此：

- 区间收益仍然可以计算；
- 共同观测日期上的最大回撤可以计算，但解释有采样限制；
- 年化日波动率被标记为不可用。

这个约束比“尽量给出一个数字”更可信。

### 比较前为什么检查价格口径和币种

前复权、未复权和总收益指数代表的经济含义不同；人民币价格和美元价格也不能在没有汇率处理时直接比较。首版遇到未知或不一致口径会阻止两资产比较，由上层 Agent 将来负责向用户澄清。

## 8. 三个指标

### 8.1 区间收益

```text
period_return = 最后价格 / 最初价格 - 1
```

价格从 100 变为 108.9，区间收益为 8.9%。它是所选价格口径的变化，不自动代表含分红总收益，也没有扣除交易成本。

### 8.2 简单收益与年化波动率

```text
r_t = P_t / P_(t-1) - 1
annualized_volatility = sample_std(r, ddof=1) × sqrt(252)
```

`ddof=1` 表示使用样本标准差，分母为 `n-1`。252 是项目默认的年化交易日假设，并不是每个市场和年份都恰好有 252 个交易日。

只有两个价格只能得到一个收益，无法计算样本标准差；至少需要三个价格、两个收益。

### 8.3 最大回撤

```text
running_peak_t = 到 t 为止的最高价格
drawdown_t = 当前价格 / running_peak_t - 1
max_drawdown = 所有 drawdown 中最小的值
```

价格 `100 → 110 → 99 → 108.9` 的最大回撤为 `99 / 110 - 1 = -10%`。峰值从分析窗口的第一个价格开始，因此改变窗口可能改变最大回撤。

## 9. 错误设计

`QuantLabError` 同时包含：

- `code`：供程序判断，例如 `NO_OVERLAP`；
- `user_message`：供界面展示；
- `retryable`：将来决定是否允许重试；
- `details`：行号、样本数等结构化信息。

程序不应该通过匹配中文或英文错误文本决定下一步。文本可能修改，而错误码是接口契约。

CSV 质量问题采用 `QualityReport` 返回，是因为我们希望一次告诉用户多个错误行；无重叠日期等无法继续的分析条件采用异常中断当前操作。

## 10. 测试如何证明代码

当前共有 26 个测试，其中 25 个单元测试分为三组，另有 1 个示例集成测试：

- `test_metrics.py`：公式和数值边界。
- `test_datasets.py`：文件与数据质量规则。
- `test_analyses.py`：日期范围、对齐、口径、会话隔离和结果组织。
- `test_example_analysis.py`：从仓库合成 CSV 导入到指标结果的完整 M1 链路。

最重要的指标测试使用手算序列 `100, 110, 99, 108.9`。年化波动率的期望值在测试中独立展开样本方差，而不是再次调用被测试函数生成答案。

另一个测试先获取 `analysis.prices_by_asset`，修改返回的 Series，再次读取分析快照。原始值仍应为 100。这证明外部拿到的只是临时副本，不能改变快照。

### 本阶段出现过的真实测试错误

第一次运行是 24 项中 23 项通过。失败测试认为原始哈希与规范化哈希一定不同。实际上，原始 CSV 如果已经是规范格式，两份字节完全相同，哈希就应该相同。

正确修复是：

- 验证 `raw_sha256` 确实等于原始字节哈希；
- 在“日期未排序”的用例中验证规范化后哈希发生变化。

没有为了通过错误测试而强行改变规范化格式。这个案例说明测试代码同样需要审查。

## 12. 建议动手练习

按顺序完成，不建议直接让 AI 给答案：

1. 手算 `100 → 90 → 99` 的区间收益和最大回撤，再调用指标函数验证。
2. 复制 `INVALID_DUPLICATE.csv` 的内容，在内存中改成相同价格的重复日期，观察系统是否仍拒绝。
3. 把 DEMO_A 的 `daily_series_complete` 设置为 false，观察波动率的 `value` 和 `unavailable_reason`。
4. 为 `DatasetMetadata` 输入带 `/` 的 asset_id，阅读 Pydantic 错误。
5. 新增一个“空 CSV”测试，并预测错误码。

练习代码不必立即提交；如果修改正式实现，应重新运行全部测试。

## 13. M1 面试表述

可以用下面的逻辑表达，不要死背措辞：

> 我先把 Agent 项目拆成确定性计算核心和模型调度层。CSV 进入系统后会经过编码、字段、日期、价格与重复记录检查，成功后生成带原始和规范化哈希的不可变快照。分析阶段固定日期范围和两资产对齐规则，再计算区间收益、样本年化波动率与最大回撤。对于日期不规则、口径不一致或样本不足的情况，系统明确降级或拒绝，而不是给出误导数字。当前 M1 使用 25 个单元测试和 1 个示例集成测试验证这些规则，Agent 工具层将在下一阶段接入。

面试时还应主动说明：当前测试都是本地确定性测试，不能被描述成真实 Agent 评估。
